# 大型前端应用怎么管理状态？从一个商品页说起

一个商品列表页有搜索框、筛选条件、商品数据和购物车。刚开始，这些状态都放在页面组件里也能正常工作。后来，导航栏要显示购物车数量，用户要分享筛选链接，浏览器点后退还要恢复之前的搜索结果。这时候就要明确**每份状态应该由谁保存，其他地方又该从哪里读取**。

## 先确定每份状态的归属

| 状态 | 放在哪里 | 原因 |
| --- | --- | --- |
| 筛选弹窗是否打开、输入框里的草稿 | 当前组件 | 只有当前组件需要 |
| 同一页面的多个组件都要用的临时筛选条件 | 共同的父组件 | 筛选面板和商品列表可以读同一份值 |
| 已提交的搜索词、分类、页码 | URL 查询参数 | 刷新、分享链接和浏览器前进后退都能恢复 |
| 访客购物车 | 按业务组织的客户端 Store | 商品页、导航栏和结算页都要使用 |
| 商品详情、库存、订单 | 服务端数据缓存 | 数据由后端维护，前端负责请求、缓存和刷新 |
| 匹配商品数量、购物车小计 | 从已有数据计算 | 商品或数量变化后，直接算出新的结果 |

同一份数据尽量只有一个来源。比如购物车里已经有每件商品的 `quantity`，导航栏需要显示总件数时，直接把数量加起来。要是另存一个 `cartCount`，那么添加商品、修改数量、清空购物车都得记得同步它。少维护一个字段，就少了一处可能不同步的地方。 [React · 选择状态结构](https://react.dev/learn/choosing-the-state-structure)

## 搜索框里的草稿和 URL 里的条件可以同时存在

假设搜索页地址是 `/products?keyword=apple&page=2`。用户在输入框里把 `apple` 改成了 `banana`，但还没点搜索。此时，输入框里的 `banana` 是**草稿**，URL 里的 `apple` 是**正在生效的查询条件**，列表继续显示苹果的结果。

点「搜索」后，页面把 URL 更新为 `/products?keyword=banana&page=1`。查询层读取新的搜索词和页码，加载香蕉的结果。之后用户按浏览器后退，URL 恢复为 `apple&page=2`，列表也恢复到之前的查询条件。

这里可以保留两份值，因为它们分别表示「正在输入什么」和「列表现在按什么条件查询」。已生效的条件以 URL 为准，页面就无需在 Store 里再维护一份相同的 `keyword` 和 `page`。

## 跨页面共享的状态，按业务收拢写入规则

购物车适合单独管理。商品页可以加购，导航栏要显示件数，结算页可以修改数量。假如这几个页面各自直接改购物车数组，「同款商品合并」和「数量为零时移除」之类的规则就容易散在各处。

可以把这些规则放在购物车模块里，对外提供 `addItem`、`setQuantity`、`removeItem` 等操作。这样，商品页和结算页调用的是同一套逻辑。导航栏只需要读取购物车并计算总件数。Vue 可以用 Pinia 的 `state`、`getters` 和 `actions` 组织这个模块，React 可以用 Redux Toolkit 的 slice。 [Pinia · Store](https://pinia.vuejs.org/getting-started.html#what-is-a-store) · [Redux Toolkit · Getting Started](https://redux.js.org/toolkit/introduction/getting-started)

要不要持久化是另一项决定。比如访客刷新页面后仍需要保留购物车，可以把购物车内容保存到本地存储。当前页面里的弹窗开关、请求加载状态，仍由各自的组件或查询管理。

## 接口数据还要考虑什么时候刷新

订单详情和订单列表可能都显示同一笔订单。用户在详情页取消订单成功后，只改详情页里的状态，返回列表时就可能看到旧的「待付款」。

如果两个页面都从查询缓存读取数据，取消成功后可以让查询层把相关的详情和列表缓存标记为过期。正在显示的查询可以重新请求，页面继续从查询结果里拿数据。像 TanStack Query 这样的工具还会维护加载、错误和重试状态，组件可以直接用这些状态来显示骨架屏或错误提示。 [TanStack Query · 服务端状态](https://tanstack.com/query/latest/docs/framework/react/overview)

以后再加一个「热门搜索」入口，只需要更新 URL，商品列表就能沿用原来的查询流程。
